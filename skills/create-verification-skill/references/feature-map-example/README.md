# Notes 検証マップ

このディレクトリは、Notes のユーザー向けの振る舞いを検証するために保守される情報源です。アプリを操作する前に索引を読み、該当する機能ファイルをレシピとして使用してください。

## 基本の前提条件

- 使い捨てのデータディレクトリを使用し、`http://127.0.0.1:4173` で Notes を起動します。
- 同時実行する処理が状態を共有しないように、`NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` を設定します。
- `Quarterly plan` と `Grocery list` というタイトルの note をシードします。
- `control-notes` と `notes` CLI に `PATH` を通します。
- `control-notes doctor` を実行し、想定する URL、データディレクトリ、ビルドリビジョンであることを必須とします。
- この検証実行で起動していないインスタンスを決して操作しないでください。

## 操作規約

- 個別の前提条件に別の記載がない限り、すべてのレシピを基本状態から開始します。
- CSS セレクターや DOM 上の位置よりも、ARIA role と accessible name を優先します。
- すべてのコマンドをリテラルとして扱います。引用符で囲まれた名前とフラグは変更しないでください。
- ブラウザ操作は `control-notes browser` から実行します。
- ターミナル操作は `control-notes cli -- <command>` から実行します。
- 変更後はシードデータを復元します。クリーンアップ中に証明用アーティファクトを削除してはいけません。

## 証明とスキップの報告

- 最終画面だけでなく、ユーザーの操作とその結果の状態を取得します。
- UI の証明には、ARIA snapshot と、アプリの識別情報が見えるスクリーンショットを含めます。
- CLI の証明には、コマンド、stdout、stderr、終了コードを含めます。
- 変更の証明には、保存された値を読み取り専用の別のビューから確認した結果を含めます。
- すべてのアーティファクトとともに、使用した機能 ID とエントリーポイントを記録します。
- 到達不能なパスは、試行したコマンドと満たされなかった前提条件とともに報告します。
- スキップしたエントリーポイントを、別のパスで検証済みと報告してはいけません。

## 機能エントリーの規約

各機能ファイルは H1 のタイトルと、ユーザーに見える振る舞いを説明する 1 つの段落で始めます。その後、正確に 4 つの H2 セクションを以下の順序で使用します。

1. `Sub-features` には、短い ID と各振る舞いの 1 行の説明を列挙します。
2. `How to get to it (user POV)` には、ユーザーのすべてのエントリーポイントを列挙します。
3. `Driving it with <harness>` は `Preconditions:` で始め、各ユーザー操作と正確なコマンドおよび観察可能な結果を組み合わせた、ラベル付きの箇条書きを使用します。
4. `Gotchas` には、検証実行を無駄にしたり無効にしたりする落とし穴を列挙します。

実装の詳細はマップに含めないでください。ユーザーパス、安定したハンドル、必要な状態、コマンド、観察可能な証明だけを記載します。

## 機能

- [note を作成する](./create-note.md) は、ブラウザと CLI での作成、キャンセル、永続化、クリーンアップを扱います。
- [note を検索する](./search.md) は、ツールバー、キーボード、CLI での検索における一致、空、クリアの各状態を扱います。
