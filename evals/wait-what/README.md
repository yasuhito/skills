# wait-what の評価

`/wait-what` の言い直しの質を、pi の実際の利用履歴で測る。
手法は [Automating eval design and hillclimbing](https://claude.dev/blog/automating-eval-design-and-hillclimbing/) に倣う。

## 仕組み

1. `extract`: `~/.pi/agent/sessions` から `/skill:wait-what` の呼び出しを抜き出し、`data/cases.json` に保存する
2. `run <variant>`: 各事例のセッションを呼び出し直前で切り、`variants/<variant>/` のスキルで pi に言い直させる (本番と同じモデル、読み取り専用ツール)。
   それを 2 つの LLM judge が 2 回ずつ採点する。`original` は履歴に残る当時の応答をそのまま採点する
   - quality (Sonnet 5): 平易さなど 5 項目を 1-5 で採点する。渡すのは直前の説明まで
   - accuracy (Opus 5.5): 言い直しの主張を一つずつ原文のまま引用させ、資料と照らして判定させる。
     誤り (矛盾、単純化による歪み、裏付けのない断定) の数はコードで数える。
     資料は、エージェントが見ていたものと同じにする。呼び出し前の会話全体 (ツールの結果と要約を含む) と、言い直しの最中に使ったツールの記録
3. `report`: 項目別の平均、1 件あたりの誤りの数、誤りのない応答の割合、2 回の採点で判定が割れた件数、謝罪で始まる応答の数 (正規表現) を出す
4. `plant` と `diagnose`: 正確さ judge の診断。言い直しに誤りを 1 つずつ混ぜた版を作り、judge がその誤りを引用して指摘できたかを数える

評価セット `data/eval-set.json` は 20 件で、ユーザーの次の発言をもとに成功 (`pass`) / 失敗 (`fail`) のラベルを付けてある。
形式は `[{"id": "<呼び出し時刻の ID>", "label": "pass" | "fail", "why": "..."}]`。

`data/` は、評価セットも含めて私的な会話の内容を含むので gitignore している。
別のマシンでは、`extract` で事例を作り直し、評価セットを手元のバックアップから戻す。

## 使い方

```sh
python3 eval.py extract
cp -r variants/v2 variants/v3   # 候補版を作って SKILL.md を 1 か所だけ変える
python3 eval.py run v3
python3 eval.py run v2 --sample s1   # ベースラインを再生成してぶれ幅を見る
python3 eval.py report v2 v2/s1 v3 -v
python3 eval.py run v3 --sample s1   # 差が微妙なら候補版も 2 回生成して
python3 eval.py compare v2 v3        # 事例ごとに比べる (全サンプルの平均、符号検定)

# judge を変えたら診断する
python3 eval.py plant v2 && python3 eval.py run v2-planted && python3 eval.py diagnose v2
```

判断のルール:

- 1 ラウンドに 1 変更
- ベースラインを 2 回生成したときのぶれ幅を超えて改善し、他の項目が下がらないときだけ採用する

## 注意

- judge の `understood` は、ユーザーの実際の反応との一致が 13/20 しかない。項目別スコアを指標にする
- 正確さ judge の診断結果 (v2 に誤りを 1 つずつ混ぜた 20 件):
  - 混ぜる前から同じ行に誤りが指摘されていた 7 件を除くと、検出は 22/26
  - 見逃しは、条件の脱落と、保証範囲の書き換えの 2 件
  - 誤りを混ぜる処理自体が、誤りになっていない文を作ることがある。診断結果は `diagnose` の出力を読んで確かめる
- 正確さの基準は、エージェントが見ていた資料との整合であり、事実そのものではない。長い会話は末尾 60000 文字だけを渡す
- `no_bad_analogy` はほぼ満点で頭打ち。改善の対象ではなく、悪化していないかを見る

## 履歴

| 版 | 変更 | plain | understood | errors | error_free | 謝罪 |
|---|---|---|---|---|---|---|
| v0 | 日本語版の初版 | 2.90 / 3.23 (2 回生成) | 0.55 / 0.68 | 1.55 / 1.32 | 0.35 / 0.33 | 17 / 14 |
| v1 | CONTEXT.md の用語は平易に言い換え、必要なものだけ使う | 4.08 | 0.93 | 1.32 | 0.25 | 12 |
| v2 | 謝罪や前置きをせず本題から始める | 4.12 / 3.95 (2 回生成) | 0.93 / 0.93 | 1.32 / 1.52 | 0.35 / 0.40 | 0 / 0 |
| v3 (不採用) | 単純化しても、条件や例外、誰が何をするかは省かない | 3.45 | 0.78 | 2.02 | 0.12 | 0 |
| v4 (不採用) | 会話やコードで確かめられたことだけを言い、推測で細部を足さない | 3.70 / 3.88 (2 回生成) | 0.88 / 0.93 | 1.00 / 1.20 | 0.50 / 0.40 | 0 / 0 |

平易にしても正確さは落ちていない。
ただし、どの版も 1 件あたり 1.3 個ほど誤りがあり、主なものは単純化による歪み (条件の脱落、因果や主語の取り違え) と、資料で確認できない断定である。
これがいま最大の改善余地で、次は `actionable` (3.75)。

v3 は細部を足そうとして応答が 1.5 倍に長くなった。
主張の数が 9.2 から 13.1 に増え、裏付けのない断定がほぼ倍増した (22 から 38)。主張あたりの誤り率も改善していない (0.143 から 0.155)。
正確さを上げるには、情報を足させる方向ではなく、確かなことに絞らせる方向を試す。

v4 はその方向を試した。長さと主張の数は v2 と変わらず、誤りだけが減った。
ただし 2 回ずつ生成して事例ごとに比べると、次のとおりだった。
- 誤りの数: 12 件で改善、5 件で悪化。符号検定で p=0.14 なので、偶然の可能性を否定できない
- 平易さ: 14 件で悪化、4 件で改善。p=0.03 で、悪化はほぼ確実
平易さを保ったまま正確さを上げる指示は、まだ見つかっていない。

微妙な差は、平均だけでなく、2 回ずつ生成した事例ごとの比較 (符号検定) で判断する。
